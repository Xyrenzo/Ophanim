# Протокол агента: как подключить свою политику

Любая программа на любом языке может работать агентом OPHANIM, если читает строки JSON из stdin и пишет
строки JSON в stdout. Оценщик запускает её отдельным процессом (или контейнером), передаёт наблюдения и
получает действия. Код OPHANIM для этого импортировать не нужно.

Полный рабочий пример только на стандартной библиотеке Python: [`examples/external_agent.py`](../examples/external_agent.py).

## Быстрый запуск

```bash
python -m ophanim run-agent --cmd "python examples/external_agent.py" --seed 7          # отдельный процесс
python -m ophanim run-agent --policy reference_auditor --seed 7                          # встроенная политика
docker build -f docker/agent.Dockerfile -t ophanim-agent:local .
python -m ophanim run-agent --container ophanim-agent:local --policy reference_auditor --seed 7   # контейнер
```

`run-agent` проводит один эпизод в закрытом режиме (агент видит награду 0.0) и печатает итог со стороны
оценщика: награду, TP/FP/FN, число шагов и причину завершения. `--config` задаёт конфигурацию эпизода,
`--trajectory` сохраняет публичную траекторию в JSONL. Это инструмент разработки на открытых эпизодах;
официальная закрытая оценка — `ophanim evaluate` и адаптер жюри.

## Сообщения

Каждое сообщение — одна строка JSON, завершённая `\n`.

```
оценщик -> агент   {"type": "reset", "observation": {...}, "info": {...}}
агент -> оценщик   {"action": {...}}
оценщик -> агент   {"type": "step", "observation": {...}, "reward": 0.0, "terminated": false, "truncated": false, "info": {}}
...
оценщик -> агент   {"type": "end"}
```

* На `reset` и на каждый `step` с `terminated = false` и `truncated = false` агент отвечает ровно одним
  действием. После `terminated` или `truncated` отвечать не нужно: следом придёт `end`.
* В stdout нельзя писать ничего, кроме сообщений протокола. Отладочный вывод — в stderr: оценщик его не
  читает и не сохраняет.

## Действия (нативный формат)

| действие | поля | что возвращает в `observation.result` |
|---|---|---|
| `list_records` | `table` (`ledger`, `invoices`, `payments`, `fx`), `cursor` (первый — `null`), `limit` 1–50 | `{table, records, next_cursor, total}` |
| `get_record` | `table`, `id` | `{table, record}` |
| `get_document` | `doc_id` | `{doc_type, document}` |
| `calculator` | `expression` (только числа, `+ - * /` и скобки) | `{result}` — точная десятичная строка |
| `submit` | `findings` = `{"episode_id", "findings": [...]}` | `{status: "submitted"}` |

Пример: `{"action": {"action": "list_records", "table": "ledger", "cursor": null, "limit": 50}}`.

Наблюдение после шага: `{ok, result, error, remaining_steps}`; при ошибке `ok = false`, `result = null`,
`error = {code, message}`. Схема выводов и правила их оценки — в [`reward_design.md`](reward_design.md).
Адаптер жюри (`judge_adapter.py`) принимает те же действия в оболочке `{"name", "args"}`.

## Коды ошибок

Ошибка — это не сбой эпизода: действие тратит шаг, эпизод продолжается (кроме `invalid_submission`,
`episode_finished` и `time_limit`). Сообщения фиксированы, ввод агента в них не повторяется.

| код | когда |
|---|---|
| `invalid_action` | действие не объект, неизвестное имя, лишние или неверные поля, сломанный JSON, строка длиннее 1 000 000 символов |
| `unknown_table` | таблицы нет (допустимы `ledger`, `invoices`, `payments`, `fx`) |
| `invalid_cursor` | курсор не выдан для этой таблицы |
| `invalid_limit` | `limit` не целое от 1 до 50 |
| `unknown_id` | записи с таким `id` в таблице нет (сравнение точное, с учётом регистра и пробелов) |
| `unknown_document` | документа с таким `doc_id` нет |
| `invalid_expression` | в выражении калькулятора есть что-то кроме чисел, `+ - * /` и скобок |
| `number_too_long` | в числе больше 30 цифр |
| `expression_too_long` | выражение длиннее 256 символов |
| `expression_too_complex` | слишком глубокая вложенность или слишком много операций |
| `division_by_zero` | деление на ноль |
| `result_out_of_range` | результат вне поддерживаемого диапазона |
| `invalid_submission` | выводы не прошли схему; эпизод завершается с наградой −1 |
| `episode_finished` | эпизод уже закончен |
| `time_limit` | исчерпано время эпизода |

## Лимиты

* 100 действий вместе с `submit`, 60 секунд на эпизод с момента `reset`, включая время самого агента.
* Строка ответа — не длиннее 1 000 000 символов (длиннее — одно `invalid_action`), весь вывод агента за
  эпизод — не больше 16 000 000 символов (больше — агента останавливают, эпизод обрывается с пустым ответом,
  причина `agent_output_limit`).
* Агент, который не отвечает, падает или закрывает stdout, получает обрыв эпизода и пустой ответ
  (`agent_timeout`, `agent_exited`).

## Окружение процесса агента

* Рабочий каталог — пустая временная папка; она же `HOME`, `TMP`, `TEMP` и `TMPDIR`. После эпизода папка
  удаляется.
* Переменные окружения — только минимальный набор (`PATH` и то, что нужно интерпретатору для запуска), плюс
  `PYTHONHASHSEED=0` для детерминированного Python. Переменные хоста, в том числе токены и любые
  `OPHANIM_*`, агенту не передаются. Если агенту действительно нужна переменная (например, путь к весам
  модели), её передают явно: `run_episode_isolated(..., extra_env={"MODEL_DIR": ...})`.
* Детерминизм: при тех же seed, конфигурации и ответах агента эпизод повторяется точно. Агенту стоит
  фиксировать собственную случайность (seed), а не зависеть от времени.

## Изоляция

Отдельный процесс — не песочница: он работает от того же пользователя ОС и видит ту же файловую систему.
Для недоверенного кода используйте контейнерный режим (`--container`): у контейнера нет сети, корневая
файловая система только для чтения, сброшены все capabilities, запрещено повышение привилегий, пользователь
65534, свои пространства имён PID и IPC, ограничения памяти, CPU и числа процессов, нет монтирований и
нет доступа к Docker-сокету хоста. Подробнее и об остаточных рисках — в
[`security_model.md`](security_model.md).
